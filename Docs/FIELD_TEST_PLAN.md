## 0-A. 実機の初回確認(トラックへ行く前に・室内で約45分＋屋外で数分)

エディタとE2Eでは確かめられず、実機で一度も見ていない項目をまとめたもの。**トラック当日の前に1回通す。**
結果は `Docs/field-tests/YYYYMMDD-precheck/` に残す(CSV・画面録画・下の記入欄)。

**前提**
- [ ] Mac に最新のエクスポートを入れる: `git pull && tools/fetch-unity-export.sh`(2026-10-14 公開の `unity-export-32541b54` 以降)

**1. 許可ダイアログ(起動〜最初の走行)**
- [ ] 出るのはカメラ・位置情報・モーション、走行開始時のヘルスケアだけ。**Bluetooth・マイクの許可ダイアログが出ないこと**
      (出たら `HeartRateReceiver.scanOnStart` / `RunAudioEngine.adaptiveVolumeFromMicrophone` がONになっていないか確認)
- [ ] 走行中、画面上部にマイク使用中のオレンジの点が出ないこと

**2. アバターの接地(`FootPlanting`)**
- [ ] 開発者モードの `avatar.footPlanting` が「メッシュ N点 / 持ち上げ …」であること。
      「骨からの概算」ならFBXのRead/Writeがビルドに反映されていない
- [ ] 歩く・その場で足踏みをしてアバターを録画し、**足が床にめり込まないこと**と、
      **踏み込むたびの持ち上げ(最大約10cm)が不自然な上下動に見えないこと**を確認(T3の前哨)

**3. フレーム時間(60fps / M2P 20ms の前提)**
- [ ] 5分ほど走行状態を続けた後(室内なら廊下を歩く)、開発者モードで次を記録:
  - `render.currentFps` — 60前後が目標(平均なのでカクつきは隠れる)
  - `render.maxFrameMs` — 走行中の最悪フレーム(起動後の累計。読み込み時は含まない)。16.6ms前後が理想
  - `render.longFrames` — 約400ms以上の引っかかりの回数。**0が目標**(1以上なら追従が一瞬ワープしうる)
- [ ] iPhoneが熱くなっていないか(発熱によるスロットリングでレイテンシが急増する)

**4. 走行ログCSV(F-11)と解析ツール**
- [ ] 開発者モードからCSVを取り出し、PCで解析する:
      `dotnet run --project tools/analyze-run-log -- <取り出したCSV>`
  - **M2P が「not measured」でないこと** — 実測値は実機でのみ出る。未計測なら `m2p.native`(開発者モード)を確認
  - **グラスへ出力中の区間も実測されていること**。提示時刻はUnityのビューが載っている画面(グラス)の
    vsyncから取る(2026-10-05〜)。抜き挿しの直後0.5秒ほどは -1 になるのが正常。
    ずっと -1 なら `ARVisionSensorTiming.mm` の画面の結び直しを疑う
  - Timeline が `100 Hz: OK`、欠落がほぼ無いこと
  - IMU が非ゼロであること(開発者モード `csv.imuSource` が `device`)
  - 室内ならGPSは未取得(`no fix`)で正常。屋外で数分歩けば位置更新と距離が出る

**5〜12 は 2026-10-13〜16 の変更(PR #5〜#9)。** どれも Windows では画面を確かめられず、まだ実機で一度も見ていない。
5〜9 は室内、10〜11 は屋外で数分歩く。12 は Mac の作業。

## 1. 計測項目(成功基準→計測方法)

| # | 成功基準(企画書§6) | 計測方法 | 合格ライン | 記録先 |
|---|---|---|---|---|
| T1 | コーナー追従の安定性 | 400mトラック2周。曲線部でアバターの不自然な挙動/ワープの有無を並走者が目視+iPhone画面録画 | ワープ0回・接線維持 | 画面録画+チェック表 |
| T2 | Motion-to-Photon ≤20ms 95% | **F-11の走行ログCSV `latency_m2p` 列(100Hz)から95パーセンタイルを算出**(主 — `dotnet run --project tools/analyze-run-log -- <CSVのフォルダ>` が算出し §3 の記入行を出す)。Swiftの`LatencyReport`(1Hz)は走行中の目視確認と`maxMs`/`overBudgetRatio`の記録に使う(従) | p95 ≤ 20ms | `Log_YYYYMMDD_HHMMSS.csv` |
| T3 | 接地精度 | 直線・コーナー・(あれば)緩傾斜でアバターの足元の浮き/めり込みを目視評価(3段階) | 全区間で「浮きなし」 | チェック表 |
| T4 | GPS精度と距離計測 | トラック既知距離(400m/周)とアプリ計測距離の誤差 | 誤差 < 3% | 統計画面のスクショ |
| T5 | 視覚的安定性(酔い) | 20分連続走行後の主観アンケート(SSQ簡易版: 酔い/眼精疲労/没入感 各5段階) | 酔い ≤ 2 | アンケート |
| T6 | 一連のシークエンス完遂 | 起動→接続→設定→走行→ゴール→統計→再走行(ゴースト)をシステムダウンなしで | クラッシュ0 | チェック表 |
| T7 | GPS喪失復帰(実地) | スタンド下・建物影を通過し、慣性→フェード→復帰演出の動作確認 | FSM通り遷移 | 画面録画 |
| T8 | 音響の実用性 | 足音/呼吸音の聞こえ方(交通騒音下含む)・環境適応音量の効き | 主観3段階で2以上 | チェック表 |
| T9 | バックグラウンド計測 | 走行中に画面ロック1分→復帰。距離・タイムの連続性確認 | 欠落なし | 統計画面 |
| T10 | 連続稼働(非機能 §10) | 走行の開始・終了の電池と走行中の最大の発熱を自動で記録(開発者モード → 実地テストの書き出し)。60分未満の走行は同じ減り方での見込み(10分以上の走行のみ・電池は5%刻み) | 60分後の電池 ≥ 30% | 書き出しの「電池・発熱」 |

## 2. 当日の実施手順

1. **セットアップ(15分)**: 機材接続 → Readyチェック全緑 → 静止状態でアバター表示確認
2. **キャリブレーション走(1周・ゆっくり)**: T3接地・T5初期感覚の確認。問題があればここで中断判断
3. **本計測(2〜3周・設定ペース走)**: T1/T2/T4を計測。並走者はコーナーでの挙動を録画
4. **シナリオ試験**: T7(建物影)→ 一時停止→再開 → T9(画面ロック)
5. **ゴール→統計確認 → ゴースト再走(1周)**: T6完遂判定
6. **クールダウン+アンケート(T5/T8)**

## 4. 中断基準

- 転倒・接触の危険を感じた時点で即中断(KPI: 重大事故ゼロが最優先)
- アバターの異常挙動(ワープ・視界の大きな揺れ)が続く場合は装着を外して原因記録
- iPhone発熱によるスロットリング(レイテンシ急増)時は休止
